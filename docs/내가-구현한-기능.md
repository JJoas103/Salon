### 1.1 AiChatController — 챗봇 중계

`src/main/java/com/soldesk/controller/AiChatController.java`

- `/api/chat` (POST) 요청을 FastAPI(`ai-service`)의 `/api/chat`으로 그대로 중계
- `RestTemplate`은 `dispatcher-servlet.xml`(웹 컨텍스트)에 정의된 빈을 생성자 주입받음. 타임아웃 connect 3초 / read 120초 — read를 길게 잡은 이유는 로컬 LLM(Ollama)이 응답까지 수십 초 걸릴 수 있어서
- 질문 길이 검증(1~500자)은 FastAPI를 부르기 전에 Spring 쪽에서 먼저 막음
- 예외 분기: `HttpStatusCodeException`(FastAPI가 4xx/5xx 응답) vs `RestClientException`(FastAPI 자체가 꺼져있어 연결 불가) — 둘 다 502로 통일해서 응답하되 메시지만 다르게
- 인증 필요 — `SecurityConfig`의 permitAll 목록에 없으므로 기본 규칙(`anyRequest().authenticated()`)을 그대로 따름 (개인 예약이력을 다루는 상담이라 로그인 요구)

### 1.2 ServiceApiController — AI가 카탈로그를 가져가는 창구

`src/main/java/com/soldesk/controller/ServiceApiController.java`, `/api/services` (GET), **permitAll** (서버 간 호출이라 브라우저 세션이 아님)

호출 흐름:
```
ai-service 기동 시 인덱스가 비어있으면 (prepare_index() 최초 1회, 또는 SalonService의 재색인 트리거)
  → GET /api/services (permitAll)
  → ServiceApiController.services()
  → SalonService.getAllServices() (@Transactional readOnly)
  → SalonMapper.findAllServices() (XML)
     SELECT ... FROM Services se JOIN Salons sal ON sal.salon_id = se.salon_id
     WHERE sal.closed_at IS NULL
     ORDER BY se.salon_id, se.service_id
```

- 폐업 매장(`closed_at IS NULL` 조건)의 시술은 카탈로그에서 자동 제외
- 이 쿼리 전용 `resultMap`이 다른 쿼리에는 없는 `salon_name` 컬럼까지 매핑 — `ServiceVO.salonName`은 DB 컬럼이 아니라 이 조인에서만 채워지는 필드 (`fb186a9`에서 추가)
- FastAPI(`elasticsearch_store.py`의 `load_products()`)가 이 JSON을 받아 "가격/소요시간/추천고민/설명" 형태의 `content` 문자열로 조립 → 이 `content`가 임베딩 벡터(SentenceTransformer)와 키워드 검색(multi_match) 양쪽의 대상이 됨

### 1.3 SalonService의 reindex 로직 — CRUD 직후 자동 재색인

`src/main/java/com/soldesk/service/SalonService.java`

- `registerService` / `updateService` / `deleteService` 세 메서드 모두, `salonMapper.insert/update/deleteService` 실행 직후 마지막 줄에서 `triggerAiReindex()` 호출
- `fastApiUrl`은 `app.properties`의 `fastapi.url`을 `@Value`로 주입받은 값 — 배포 환경이 바뀌면 이 프로퍼티만 바꾸면 됨 (다만 `app.properties`의 주석은 "AiChatController가 이 값으로 호출"이라고만 적혀 있어서, 실제로는 `SalonService`도 같은 프로퍼티를 쓴다는 사실은 주석만 봐서는 안 드러남)
- 예외 처리: FastAPI가 꺼져 있어 `RestClientException`이 나도 `log.warn`만 남기고 리턴 — 예외를 다시 던지지 않으므로 `@Transactional`이 롤백되지 않고, 점주의 시술 등록/수정/삭제 자체는 항상 정상 커밋됨
- FastAPI 쪽(`/api/reindex`)이 하는 일: `GET /api/services` 재조회 → 각 상품 `content`를 SentenceTransformer로 임베딩 벡터화 → 기존 `salon-services-agent` 인덱스를 통째로 삭제 → 매핑 재생성 → `helpers.bulk`로 전체 재삽입 → refresh → `{created, index, document_count, message}` 반환
- **왜 부분 갱신이 아니라 매번 통째로 재생성하나**: 카탈로그 규모가 작아서, "삭제된 시술이 인덱스에 남아있는" 같은 부분 갱신 정합성 버그를 아예 원천 차단하는 쪽을 선택한 설계

### 1.4 발표 Q&A 대비 — 미묘한 타이밍 포인트

`registerService()`는 `@Transactional`이고, 그 메서드 안에서 `insertService()` 다음 줄로 `triggerAiReindex()`를 **동기 HTTP 호출**로 실행한다. 이 호출은 FastAPI → `load_products()` → 다시 Spring의 `GET /api/services`로 돌아오는데, 이건 완전히 별개의 새 HTTP 요청(별도 스레드, 별도 트랜잭션)이다.

DB 연결은 `DriverManagerDataSource`(커넥션 풀 없음, 매번 새 연결, `applicationContext.xml`)를 쓰기 때문에 원래 트랜잭션의 커넥션과 재색인 조회의 커넥션은 서로 다르다. `registerService()`의 트랜잭션은 메서드가 끝나야 커밋되는데, `triggerAiReindex()` 호출 시점엔 아직 메서드가 끝나지 않았으므로 커밋 전 상태다. MySQL/MariaDB 기본 격리수준(REPEATABLE READ)에서는 커밋 전 데이터가 다른 커넥션에는 보이지 않으므로, 이론적으로는 방금 등록한 시술이 이번 재색인에는 빠지고 다음 CRUD 때 재색인되면서 뒤늦게 반영될 수 있다.

심각한 버그는 아니다(다음 CRUD나 ai-service 재기동 시 정합성은 맞춰짐). 발표 자료에는 "완벽한 실시간까진 아니고 사실상 실시간(near real-time)"이라고 설명하면 정확하다.

### 1.5 개인화 — 로그인 사용자의 예약이력 반영

`AiChatController.java`, `vo/{ChatRequest,ReservationVO}.java`, `resources/mapper/ResvMapper.xml`, `ai-service/chat/{schemas.py,router.py,main.py}`

- FastAPI는 MySQL에 직접 접근하지 않는다. 개인화에 필요한 예약이력은 Spring이 조회해서 문자열로 조립한 뒤 `ChatRequest.userContext` 필드에 담아 넘긴다 — FastAPI 쪽에 DB 자격증명을 하나 더 늘리지 않기 위한 선택이자, 인증(로그인 여부)이 Spring Security에만 있다는 사실과도 맞물린다.
- `ChatRequest`에는 `question`/`sessionId`와 함께 `userContext` 필드가 있지만, 클라이언트(브라우저 JS)는 이 필드를 채워 보내지 않는다. `AiChatController.chat()`이 요청을 받자마자 `Authentication` 파라미터(스프링 시큐리티가 세션에서 채워줌)로 로그인한 사용자의 이메일을 얻고, 그 값으로 `userContext`를 서버가 직접 덮어쓴다. 클라이언트가 임의로 `userContext`를 채워 보내도 무시되므로, 다른 사람의 예약이력을 사칭해서 보낼 수 없다.
- `buildUserContext()`가 하는 일: `userService.getUser(email)`로 `userId`를 얻고 → `reservationService.getRevList(userId)`(마이페이지 예약내역 조회와 같은 메서드)로 그 사용자의 전체 예약을 가져온 뒤 → `status`가 `"completed"`인 것만 남기고 → `LinkedHashSet`으로 중복 시술명을 제거하면서 최근 순으로 최대 5개까지만 → `"시술명(카테고리, 매장명)"` 형태 문자열로 합친다(예: `"여성컷(컷, 라움헤어), 발레아쥬(염색, 뮤즈헤어살롱)"`). 매장명은 나중에 `8482f57`에서 덧붙였다 — 매장까지 넘기지 않으면 LLM이 어느 매장이었는지 추측해서 답한다. completed가 하나도 없으면 `null`을 넘긴다.
- `getRevList`가 원래 조인하던 컬럼(`Salons`/`Services`/`Payments`)에는 `category`/`concern`이 빠져 있었다. `ResvMapper.xml`의 `getRevList` select에 `se.category, se.concern`을 추가하고 `ReservationVO`에도 필드를 늘려서, 마이페이지 예약내역 화면에는 영향 없이 개인화용 데이터만 얹었다.
- FastAPI(`chat/schemas.py`)는 `userContext`를 `user_context`(alias)로 받고, `chat/router.py`가 이를 `McpChatService.ask(session_id, question, user_context)`로 그대로 전달한다.
- `McpChatService.ask()`는 세션(대화방)의 **첫 턴에만** — 즉 `history`가 비어있을 때만 — `"[사용자 예약 이력] 완료한 시술: ..."` 문장을 `HumanMessage`로 질문 앞에 끼워 넣는다. 이 메시지는 그 세션의 대화기록(`_messages_by_session`)에 그대로 남기 때문에, 두 번째 질문부터는 다시 넣지 않아도 LLM이 이전 맥락으로 계속 참조할 수 있다. 매 턴 반복해서 넣지 않는 이유는 프롬프트 길이 낭비를 막기 위해서다.
- `create_agent`의 `system_prompt`에도 "예약 이력이 있으면 참고해서 우선 추천하되, 이력에 없는 내용을 근거로 지어내지 말 것"이라는 지침을 한 줄 추가했다 — MCP 검색 결과만 근거로 답하라는 기존 원칙과 개인화 지침이 충돌하지 않도록, "이력은 취향 힌트일 뿐 시술 정보의 근거는 여전히 Tool 결과"라는 우선순위를 명시한 것이다.
- **검증**: `test1@salu.com`은 완료 예약이 컷/염색 각 1건씩 있다. curl로 로그인 후 세션 쿠키로 Spring `/api/chat`에 "나한테 어울리는 시술 추천해줘"라고만(구체 시술명 언급 없이) 물었더니 답변에 "컷"과 "염색"이 그대로 언급됨 — 개인화 컨텍스트가 실제로 반영된다는 것을 확인했다. 다만 그 답변 자체는 "해당 카테고리엔 맞는 시술이 없다"로 끝났는데, 이는 에이전트가 `search_service` 툴에 카테고리 인자를 하나만 넣을 수 있는데 두 카테고리를 동시에 요구하려다 생긴 별개의 툴 사용 이슈다(배선 문제 아님, 개선 여지로 남겨둠).

### 1.6 질문 갈래를 백엔드가 먼저 정함 — `4abab0f`

`ai-service/chat/intent.py`(신규), `chat/main.py`

문제는 모델 크기였다. 로컬에서 돌릴 수 있는 크기의 모델은 "주차 되나요?" 처럼 카탈로그에 아예 없는 정보를 물으면 그럴듯한 답을 지어낸다. 검색 도구를 쥐여줘도, 도구를 부를지 말지의 판단 자체를 모델에게 맡기면 자주 건너뛴다.

그래서 **무엇을 물었는지는 코드가 정하고, LLM 에게는 그 갈래에 필요한 데이터만 미리 쥐여주는** 쪽으로 뒤집었다. `classify()` 가 질문을 다섯 갈래로 나눈다.

| 인텐트 | 예시 질문 | 처리 |
|---|---|---|
| `OUT_OF_SCOPE` | 주차 되나요? | LLM 을 아예 호출하지 않고 고정 문구 반환 |
| `SALON_MENU` | 내가 갔던 매장에 뭐가 있어? | 이력 매장으로 필터한 카탈로그를 주입 |
| `SALON_FIND` | 평점 좋은 매장 추천해줘 | `salons` 인덱스 조회 결과를 주입 |
| `CATALOG_LIST` | 제일 저렴한 시술이 뭐야? | 정렬된 전체 목록 도구를 쓰게 함 |
| `SERVICE_SEARCH` | 손상모 케어 시술 추천해줘 | 기본값. 관련도 검색 |

설계상 짚어둘 점.

- **분류를 LLM 에게 시키지 않고 정규식으로 한다.** LLM 분류를 넣으면 호출이 한 번 더 붙어 응답이 20초 가까이 늘어난다. 대신 확실한 것만 잡고 애매하면 `SERVICE_SEARCH` 로 떨어뜨려서 오탐 피해를 줄였다.
- **차단 갈래는 LLM 을 타지 않는다.** 주차·영업시간·예약변경·쿠폰·의학상담·계정 여섯 가지는 인덱스 어디에도 없어서 답하려면 지어낼 수밖에 없다. 27초 걸려 틀린 답을 내던 것이 0.05초에 정확한 안내로 바뀌었다.
- **검사 순서가 결과를 바꾼다.** `SALON_MENU`(특정 매장의 메뉴)가 `SALON_FIND`(매장 고르기)보다 좁으므로 먼저 검사한다. 순서를 뒤집으면 "내가 갔던 매장에 뭐가 있어?" 가 매장 추천으로 샌다.
- `CONSULT`(증상만 말한 상담) 갈래도 만들었다가 **뺐다.** "손상모 케어 추천해줘" 같은 정상 검색까지 되묻기로 새어나가서, 규칙 대신 프롬프트의 "추천 먼저, 질문은 마지막" 규칙에 맡겼다.
- **예약 이력이 없는 사용자의 이력 질문도 같은 방식으로 끊는다**(`4917175`). 이력이 없으면 LLM은 근거가 없어 "대화 내용에 없습니다" 같은 엉뚱한 답을 내놓는데, 답이 나올 수 없는 질문에 40초를 쓰고도 안내가 되지 않는다. 다만 `SALON_MENU` 전체를 막으면 안 된다 — "라움헤어에 뭐가 있어?"는 이력 없이도 답할 수 있다. 그래서 `needs_history()`가 이력을 가리키는 표현(`내가 갔던`, `단골`, `저번에 받은`, `자주 가는`)만 따로 잡는다.

### 1.7 순위·전량 질문용 도구 추가 — `0da88ed`

`ai-service/mcp_chat/mcp_product_server.py`, `search/elasticsearch_store.py`

기존 `hybrid_search` 는 관련도 상위 몇 건만 돌려주는 구조라 "제일 저렴한 시술이 뭐야?" 에 **구조적으로** 답할 수 없다. 상위 5건 안에 최저가가 없으면 그냥 틀린 답이 나온다. 그래서 정렬·전량 조회 전용으로 `list_catalog(category, salon, sort_by, order, count)` 를 따로 만들었다.

- 매장 필터는 ES 가 아니라 **파이썬에서 후처리**한다. nori 형태소 분석기가 "라움헤어" 를 쪼개면서 "헤어" 토큰이 "위드헤어"/"블랑쉬헤어" 까지 끌고 와, 2건이어야 할 결과가 8건이 됐다.
- 도구 정의는 반드시 `if __name__ == '__main__': mcp.run()` **앞에** 둬야 한다. `mcp.run()` 이 블로킹이라 그 뒤의 데코레이터는 실행되지 않는다. 처음에 뒤에 뒀다가 도구가 통째로 등록되지 않았다.

`SALON_FIND` 용으로는 `search/salon_store.py`(신규)가 `salons` 인덱스를 본다. 시술 인덱스에는 평점도 주소도 없어서 "어디가 잘해요" 에 답할 수 없는데, 그 정보는 매장 검색 기능이 쓰던 별도 인덱스에 이미 있었다.

### 1.8 모델 교체와 provider 스위치 — `d0f6089`

`ai-service/llm.py`

15문항 회귀 테스트로 골랐다. 8B 는 카탈로그에 없는 시술을 지어냈고 응답이 최대 162초까지 튀어 `readTimeout` 120초를 넘겼다. 9B 는 같은 문항에서 환각 0건, 총 468초(8B 는 931초)로 오히려 빨랐다 — 헤매지 않아서다. 14B 는 품질 차이가 크지 않은 데 비해 요구 메모리가 커서 뺐다.

**사고(reasoning) 모드는 껐다.** qwen3.5는 사고형 모델이라 생각을 `thinking` 필드로 따로 내보내는데, 그 턴을 생각으로만 채우고 본문을 비워 보내는 일이 있어 빈 말풍선이 나갔다. Ollama를 직접 호출해보면 `"response":"", "thinking":"Thinking Process:..."` 로 찍힌다. 시술 상담은 검색 결과를 정리해 보여주는 일이라 긴 추론이 필요하지 않고, 끄면 평균 30초 → 25초로 빨라진다.

`llm.py` 는 강사 완성본이 OpenAI 전용이던 것을 provider 스위치 구조로 다시 썼다. `LLM_PROVIDER=openai` 로 두면 `ChatOpenAI`, 기본값이면 `ChatOllama` 를 돌려준다. 발표 당일 로컬 추론이 불안하면 환경변수 하나로 갈아탈 수 있게 남겨둔 장치이고, 실제 사용에는 API 키와 `langchain-openai` 설치가 추가로 필요하다.

### 1.10 ai-service 실행 방법

`ai-service/run.sh`

```bash
./ai-service/run.sh          # 로컬 Ollama(localhost:11434) 로 기동
./ai-service/run.sh --fg     # 로그를 화면에 띄운 채 실행
```

스크립트로 감싼 이유가 있다. `python app.py` 로 직접 띄우면 두 가지가 자주 어긋난다.

1. **이전 프로세스가 8000 을 쥔 채 남는다.** 새로 띄운 줄 알고 옛날 코드로 계속 답한다. 실제로 `intent.py` 를 고친 뒤 재기동을 안 해서 수정이 반영되지 않은 채 테스트한 적이 있다. `uvicorn` 을 reload 없이 띄우므로 파일만 고쳐선 바뀌지 않는다.
2. **어느 Ollama 를 보는지 눈에 안 보인다.** 환경변수로 원격을 지정해두면 로컬에서 도는 줄 알고 성능을 오판한다.

그래서 `run.sh` 는 포트를 먼저 비우고 → Ollama/Elasticsearch 생존을 확인하고 → 모델이 실제로 받아져 있는지까지 본 뒤 → 어디에 붙는지 찍고 기동한다. 의존 서비스가 죽어 있으면 기동 전에 알려주므로, 첫 질문에서야 실패를 발견하는 일이 없다.

선행 조건은 세 가지다.

```bash
sudo systemctl start ollama       # Ollama
ollama pull qwen3.5:9b            # 모델 (약 6GB)
docker start <es-container>       # Elasticsearch (localhost:9200)
```

모델은 코드 수정 없이 환경변수로 바꿔 시험할 수 있다. `run.sh`가 그 모델이 실제로 받아져 있는지 먼저 확인하고, 없으면 `ollama pull` 명령을 알려주고 멈춘다.

```bash
OLLAMA_MODEL=qwen3:8b ./ai-service/run.sh    # 다른 모델로 바꿔 테스트
```

### 1.11 질문 하나가 답변이 되기까지 — 실제 입력 추적

발표에서 "AI가 알아서 답합니다"로 끝내면 질문을 받는다. 실제로 무엇이 어떻게 바뀌어 들어가는지 찍어둔다.

```
질문
 ↓
[1] 정규식으로 갈래 판정              ← LLM 개입 없음, 0.02초
 ↓
[2] 갈래에 맞는 ES 조회 → 프롬프트에 주입   ← SALON_FIND / 이력 있을 때만
 ↓
[3] 메시지 조립해서 LLM 호출
 ↓
[4] LLM이 필요하면 도구 호출            ← 주입이 있으면 대개 생략됨
```

**ES를 때리는 시점이 두 군데로 갈린다**는 것이 핵심이다. 백엔드가 미리 조회해서 넣어주거나, LLM이 도구로 직접 부르거나.

**"손상모 케어 시술 추천해줘"** — 주입 없이 LLM이 도구를 고르는 경우

```
[1] service_search (기본값)
[2] 주입 없음
[3] LLM 입력 3개 / 1,098자
      1. 220자  프롬프트 템플릿 (MCP prompt)
      2. 864자  SEARCH_GUIDE (MCP resource)
      3.  14자  손상모 케어 시술 추천해줘        ← 사용자 원문 그대로
[4] prepare_service_index({})
    search_service({"query": "손상모 케어"})
      → 5건: 손상모 집중케어 / 남성컷 / 클리닉트리트먼트 / 탈색모 클리닉 / 베이직 트리트먼트
```

사용자 문장이 `query`로 바뀌는 것은 LLM이 한다. "손상모 케어 시술 추천해줘" → `query="손상모 케어"` 로 조사와 요청어를 떼어낸다. 이 변환 규칙이 864자짜리 `SEARCH_GUIDE`에 적혀 있다(`5만원 이하`→`max_price=50000` 같은 것). ES에서는 이 `query`가 nori 형태소 분석과 임베딩 벡터 양쪽으로 검색되어 `concern` 필드의 "손상모, 갈라짐, 푸석함 완화"와 매칭된다.

**"제일 저렴한 시술이 뭐야?"** — 도구를 갈아타는 경우

```
[1] catalog_list
[4] list_catalog({"sort_by": "price", "order": "asc", "count": 1})
      → 위드헤어 남성컷 15,000원
```

`search_service`가 아니라 `list_catalog`를 부른 것이 핵심이다. 관련도 검색은 상위 몇 건만 주므로 최저가를 구조적으로 못 맞춘다.

**"평점 좋은 매장 추천해줘"** — 백엔드가 ES를 먼저 때리는 경우

```
[2] salons 인덱스 조회 결과를 통째로 주입

    [등록된 매장 평점순 목록]
    - 뮤즈헤어살롱 / 평점 4.9 / 최저 24,000원 / 인천 미추홀구 주안동 90-1 / 20년 경력...
    - 살롱드밀 / 평점 4.8 / 최저 90,000원 / 서울 성동구 성수동 56-7 / 연예인 단골...
    이 목록에 없는 매장은 존재하지 않습니다. 평점과 가격은 이 값만 사용하세요.
                                                ↑ 이 한 줄이 환각을 막는다

[3] LLM 입력 4개 / 1,490자
[4] 도구 호출 없음 — 주입된 데이터만으로 답함
```

정렬 기준도 백엔드가 정한다. 질문에 `저렴/싼/가격/저가`가 있으면 최저가순, 아니면 평점순이다.

**"내가 갔던 매장에 뭐가 있어?"** — 이력에서 매장명을 파싱하는 경우

```
[2] "레이어드컷(컷, 라움헤어), 핑크 컬러(염색, 컬러플레이 헤어)"
      → 괄호 안 마지막 항목만 → ['라움헤어', '컬러플레이 헤어']
    각 매장으로 list_services 조회 → 주입

    [이력 매장이 취급하는 시술 전체]
    - 라움헤어: 남성컷(컷/18000원), 여성컷(컷/25000원), 레이어드컷(컷/32000원),
                앞머리펌(펌/35000원), 헤어글로스(클리닉/45000원), 애쉬브라운 염색(염색/85000원)
    - 컬러플레이 헤어: 컬러 커트(컷/30000원), 탈색모 클리닉(클리닉/80000원), ...
    이 목록에 없는 시술은 해당 매장에서 받을 수 없습니다.

[3] LLM 입력 5개 / 1,420자
[4] 도구 호출 없음
```

**주입하면 도구 호출이 사라진다.** 이것이 이 설계의 실측 근거다.

| 질문 | 주입 | LLM 도구 호출 | 응답 |
|---|---|---|---|
| 손상모 케어 시술 추천해줘 | 없음 | 2회 | ~30초 |
| 제일 저렴한 시술이 뭐야? | 없음 | 1회 | ~33초 |
| 평점 좋은 매장 추천해줘 | 있음 | **0회** | ~22초 |
| 내가 갔던 매장에 뭐가 있어? | 있음 | **0회** | ~21초 |

"작은 모델에는 데이터를 미리 쥐여준다"는 원칙이 환각 방지뿐 아니라 속도에도 효과가 있다 — LLM↔도구 왕복이 통째로 사라지기 때문이다.

### 1.12 운영 중 터진 것과 고친 것

교과서적인 설계보다 이쪽이 질문을 많이 받는 대목이다.

**상담 하나가 멈추면 서비스 전체가 잠겼다** (`b529f1d`)

`_invoke_lock`으로 상담을 한 번에 하나씩 처리하는데 여기에 상한이 없었다. 요청 하나가 멈추면 이후 모든 상담이 무한정 대기하고, **재기동 말고는 복구 수단이 없었다.** 실사용에서는 사용자가 탭을 닫기만 해도 재현된다.

진단이 까다로웠던 이유는 증상이 "AI 서버가 느리다"로 보였기 때문이다. 갈라낸 방법은 이렇다.

```
Ollama 직접 호출              1.3초    ← 완전 정상
ai-service 경유             145초 무응답
그 요청이 Ollama를 부른 횟수    0번     ← Ollama에 닿기도 전에 막힘

차단 질문 ("주차 되나요?")     0.02초   ← 락을 거치지 않는 경로
일반 질문 ("컷 얼마야?")       40초 무응답  ← 락이 필요한 경로
```

**차단 질문은 빠른데 일반 질문만 느리면 락 물림이다.** 락 획득 25초 / 에이전트 90초로 끊었고, 합이 115초라 Spring의 `readTimeout` 120초 안에 들어온다. 시간을 넘기면 MCP 세션을 버려서 다음 요청이 새로 연결한다 — 버리지 않으면 이후 요청도 전부 같은 자리에서 90초씩 까먹는다.

**빈 말풍선이 나갔다** (`b529f1d`)

원인은 1.8의 사고 모드였다. 방어책으로 `_final_answer()`가 마지막 메시지를 그냥 쓰지 않고 뒤에서부터 내용이 있는 `AIMessage`를 찾는다. 그래도 비면 "답변을 정리하지 못했습니다"를 돌려준다.

**답변에서 매장명이 눈에 안 띄었다** (`195b271`)

가격·소요시간은 라벨을 달고 매장명만 괄호에 들어가서, 예약에 제일 먼저 필요한 정보가 묻혔다. 사용자가 "어떤 가게?"를 한 번 더 물어야 했다. `SEARCH_GUIDE`에 답변 형식 규칙을 넣어 매장명을 첫 항목으로 올렸다.

**수정했는데 반영이 안 됐다**

`uvicorn`을 reload 없이 띄우므로 파일만 고쳐선 바뀌지 않는다. `intent.py`를 고친 뒤 재기동을 안 해서, 이미 고친 버그(`영업시간는` 조사 오류)가 계속 재현된 적이 있다. 1.10의 `run.sh`가 이걸 막는다.

### 1.13 시연용 시드 데이터 — `4df29de`

`sql/seed_ai_demo.sql`

## 3. 점주(Owner) 예약현황판 + 예약 거절/노쇼 처리 — `52ffedc`

`/owner/reservations` (`OwnerController`) + `ReservationService`

### 예약현황판 (Grid)

`ReservationService.getScheduleBoard()`가 하루치 표를 만든다.

- 표의 행(시각)은 **디자이너 근무시간 슬롯**과 **실제 예약 시각**을 합쳐서 생성. 근무시간을 나중에 줄이거나 휴무로 바꿔도 이미 잡힌 예약이 표에서 사라지지 않도록, 근무시간 밖이라도 예약이 있으면 행을 만들고 `isOutsideHours`로 경고 표시
- 디자이너 수와 무관하게 DB 조회는 4번(디자이너 목록/영업시간/그날 스케줄/그날 예약)으로 고정
- 30분 단위 슬롯(`SLOT_MINUTES`)이 기본이지만, 펌처럼 소요시간이 긴 시술은 `coveredBy()`로 이후 슬롯까지 "점유중"으로 표시
- `fillDisplayFields()`가 DB의 `status`는 건드리지 않고, 현재 시각 + 시술 소요시간만으로 화면 표시값(`예약됨/진행중/완료/결제중/결제 미완료/거절됨/노쇼/취소됨`)을 그때그때 계산 — 커트 30분과 펌 90분이 서로 다른 시점에 "완료"로 바뀌는 이유

### 예약 거절 / 노쇼 처리

`ReservationService.rejectReservation()` — `Reservations`에 `reject_reason`/`cancel_type` 컬럼 추가(`migration_reservation_reject.sql`)

- **거절(rejected)**: 매장 사정으로 취소 → 결제 완료건이면 카카오페이 환불(`kakaoPayService.cancel`) + 적립금/쿠폰 원복(`pointService.restore`, `couponService.refund`)까지 한 트랜잭션에서 처리
- **노쇼(no_show)**: 손님이 안 옴 → 환불 없음(선불 금액은 매장이 가짐), 적립금/쿠폰도 원복하지 않음 — 환불이 없는데 적립금만 돌려주면 그 차액을 플랫폼이 떠안게 되므로 원복 여부는 항상 환불 여부와 같이 감
- 검증 순서 = 방어 순서: 사유 값 → 예약 존재 → 소유 매장 확인 → 상태(`confirmed`인지) → 시점(노쇼는 예약 시각이 지난 뒤에만 가능, 아직 오지 않은 손님을 노쇼 처리할 수 없음)
- 카카오 환불이 실패하면 예외로 트랜잭션 전체 롤백 → 예약은 `confirmed`로 남음 (환불 없이 예약만 취소되는 상태가 가장 위험하므로 이 순서로 방어)
- `resvMapper.rejectReservation()`의 UPDATE 문에도 `status='confirmed'` 조건이 걸려있어, 검증 통과 후 다른 요청이 먼저 처리했으면 0행 갱신 → 이 경우도 실패로 보고 롤백 (동시 처리 경합 방지)
